# Вторая конфигурация: контроль потока данных (OpenAPPA)

Карточка проекта требует две конфигурации на одних сценариях: «только OPA» и «OPA + OpenAPPA». Живой стенд (`../stand/`) — это конфигурация «только OPA»: шлюз + адаптер + OPA решают по каждому вызову.

Здесь — вторая: **контроль потока**. Он ловит то, чего авторизация по вызову не видит в принципе — цепочку «прочитал приватное → прочитал недоверенное → отправил наружу» (lethal trifecta). Каждый вызов в ней OPA бы разрешил: все три инструмента агенту допущены.

`appa replay --config flow/contract.toml -v flow` прогоняет трассу: внешняя отправка после чтения приватного тикета **отклоняется**, внутренняя — проходит.

**Ограничение исполнения (честно).** Это НЕ живой sidecar внутри стенда. У CLI `appa` 0.34.0 нет HTTP-эндпоинта проверки по вызову — есть `replay` (трасса целиком). Живой перехват по вызову даёт отдельный компонент `appa-runtime` (библиотека/платформа Archestra), не standalone-бинарь. Поэтому вторая конфигурация показана детерминированной трассой через `appa replay`, а не подключением к адаптеру. Интерфейс адаптера под неё готов (`FLOW_URL`, см. `adapter/adapter.py`), обёртку над `appa-runtime` писать, когда он будет доступен.

Контракт — сокращённая модель (литеральные аудитории, без внешнего источника с OAuth), как и в проекте 03.
